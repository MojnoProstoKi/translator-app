# Research: Перевод речи собеседника в реальном времени (macOS)

Все пункты Technical Context, отмеченные как требующие исследования, разрешены ниже.

## 1. Потоковое on-device распознавание речи (ASR)

**Decision**: Apple `SpeechAnalyzer` + `SpeechTranscriber` (framework **Speech**, macOS 26+).

**Rationale**: Начиная с iOS/macOS 26 Apple заменила устаревший `SFSpeechRecognizer` на
`SpeechAnalyzer`/`SpeechTranscriber` — API, спроектированный именно под потоковое и
долгоформатное распознавание на устройстве, с низкой задержкой и автоматическим управлением
языковыми моделями. По опубликованным данным это на ~2.2× быстрее сопоставимой модели
Whisper Large-V3 Turbo при WER 2.12% (чистая речь) / 4.56% (шум) на LibriSpeech. Так как FR-006
требует полностью локальной обработки, а FR-004/FR-005 требуют инкрементального
частичного/уточняемого перевода, потоковый API с встроенной поддержкой partial results снимает
необходимость городить собственную буферизацию/чанкинг поверх более старого `SFSpeechRecognizer`
(его `requiresOnDeviceRecognition` также поддерживает `shouldReportPartialResults`, но требует
ручной загрузки языковых ассетов и не оптимизирован под длинные потоковые сессии).

**Alternatives considered**:
- `SFSpeechRecognizer` (устаревший, on-device режим) — работает, но менее точен в offline-режиме,
  требует отдельной загрузки языковых моделей через системные настройки и не даёт таких же
  гарантий по задержке для длинных непрерывных сессий.
- `WhisperKit` (Argmax, Swift-пакет поверх CoreML Whisper) — полноценный потоковый режим, хорошая
  поддержка Apple Silicon (ANE/GPU), но добавляет внешнюю зависимость и модель, которую нужно
  бандлить/скачивать отдельно, что противоречит принципу Simplicity при наличии равноценного
  первоклассного API от Apple. Стоит держать в уме как запасной вариант, если потребуется
  поддержка более старых версий macOS, где `SpeechAnalyzer` недоступен.
- `whisper.cpp` напрямую — та же логика, что и WhisperKit, но менее нативна для Swift-проекта,
  требует ручной работы с C++ bridging.

## 2. On-device машинный перевод (MT)

**Decision**: Apple **Translation** framework (`TranslationSession`, доступен с macOS 14.4).

**Rationale**: Первоклассный, бесплатный, полностью on-device перевод текста с автоматической
загрузкой офлайн-языковых пакетов; не требует сети после первоначальной загрузки языковой пары
en↔ru. Прямая интеграция с SwiftUI/AppKit, что минимизирует связующий код. Соответствует FR-006
(запрет на внешние сетевые вызовы) без дополнительных зависимостей.

**Alternatives considered**: Bundling локальной NMT-модели (например, NLLB через CoreML) —
избыточная сложность и больший размер приложения без явного выигрыша в качестве для пары
en→ru по сравнению с first-party решением; отклонено по Simplicity/YAGNI.

## 3. Захват системного звука

**Decision**: **Core Audio Taps** (`AudioHardwareCreateProcessTap`, `CATapDescription`,
macOS 14.4+), запрашивающие только разрешение «System Audio Recording».

**Rationale**: Начиная с macOS 14.2/14.4 Core Audio Taps позволяет захватывать системный звук
(весь вывод или по конкретным процессам) без более широкого разрешения «Screen & System Audio
Recording», которое требует `ScreenCaptureKit`. Поскольку приложению не нужно захватывать
видео/экран — только звук, — Core Audio Taps даёт более узкий и понятный пользователю запрос
разрешения, что лучше соответствует FR-010 (явные, понятные запросы доступа) и общей
privacy-ориентированности продукта.

**Alternatives considered**: `ScreenCaptureKit` (`SCStream` с аудио-конфигурацией) — тоже
поддерживает захват системного звука (в т.ч. по конкретным приложениям, что удобно для
избирательного захвата только звонка в Zoom/Teams), но требует более широкого разрешения на
запись экрана и вынуждает либо игнорировать видеокадры, либо отдельно их не запрашивать. Может
быть добавлен позже как опция «захват звука конкретного приложения», если потребуется более
точная фильтрация источника, чем «весь системный звук».

## 4. Захват микрофона

**Decision**: `AVAudioEngine` (стандартный, стабильный API захвата аудио с микрофона в реальном
времени, совместим по формату буферов с `SpeechAnalyzer`).

**Rationale**: Штатное решение для низкоуровневого захвата аудио на macOS, широко используется
совместно со Speech-фреймворком.

**Alternatives considered**: Не рассматривались — выбор не создаёт архитектурных рисков и
является стандартной практикой платформы.

## 5. Минимальная версия macOS и требования к оборудованию

**Decision**: macOS 26 (Tahoe) и новее, Apple Silicon (M1 или новее).

**Rationale**: Наиболее требовательный компонент — `SpeechAnalyzer`/`SpeechTranscriber` —
доступен только с macOS 26; Core Audio Taps требует macOS 14.4+; Translation framework — macOS
14.4+. Итоговый минимум определяется самым новым требованием. Так как вся обработка выполняется
on-device в реальном времени (ASR + MT одновременно с воспроизведением звонка), Apple Silicon
(Neural Engine/GPU) необходим для приемлемой задержки (SC-001); Intel Mac не рассматривается для
MVP.

**Alternatives considered**: Понижение минимальной версии до macOS 14.4 путём замены ASR на
`SFSpeechRecognizer` или `WhisperKit` — отклонено для MVP в пользу более точного и быстрого
first-party API; может быть пересмотрено отдельным решением, если потребуется поддержка более
широкого парка устройств.

## 6. Локальное хранение расшифровок сессий

**Decision**: Один JSON-файл на сессию в
`~/Library/Application Support/<bundle-id>/Sessions/<session-id>.json`.

**Rationale**: Данные однопользовательские, объём умеренный (текст, не аудио), запросы простые —
список файлов (FR-016) и удаление конкретного файла (SC-006, ≤2 действия в UI). Использование
базы данных (например, SQLite/GRDB) добавило бы зависимость и миграционную сложность без
измеримой пользы на этом объёме данных — отклонено по Simplicity/YAGNI (Constitution Principle
V).

**Alternatives considered**: SQLite через GRDB.swift — даёт транзакционность и удобные запросы,
но избыточна для CRUD-операций над независимыми записями фиксированной, некрупной схемы.

## 7. Плавающий always-on-top оверлей

**Decision**: `NSPanel` с `styleMask: .nonactivatingPanel`, `level: .screenSaver` (или
`.floating` с `collectionBehavior` вкладками `.canJoinAllSpaces` + `.fullScreenAuxiliary`),
содержащий SwiftUI-контент через `NSHostingView`.

**Rationale**: Стандартный macOS-паттерн для плавающих небольших окон, которые должны быть видны
поверх полноэкранных приложений и на всех Spaces без кражи фокуса у активного приложения (звонка).
`.nonactivatingPanel` не забирает фокус ввода при появлении, что критично, чтобы не мешать
разговору в Zoom/Teams.

**Alternatives considered**: Обычное `NSWindow` — не поддерживает поведение
non-activating/floating без существенных обходных путей; отклонено.

## 8. Стратегия тестирования потокового аудиопайплайна

**Decision**: Интеграционные тесты подают заранее записанные короткие WAV-фикстуры (английская
речь с известной эталонной расшифровкой) на вход реального пайплайна `SpeechAnalyzer` →
`TranslationSession` и проверяют: (а) появление хотя бы одного частичного результата до
завершения аудиофайла, (б) содержание финального перевода ожидаемых ключевых слов, (в) время до
первого частичного результата в пределах SC-001.

**Rationale**: Соответствует Constitution Principle IV — запрет на моки on-device провайдеров в
интеграционных тестах; фикстуры делают тесты детерминированными и воспроизводимыми на CI без
живого микрофона/звонка.

**Alternatives considered**: Моки `ASRProvider`/`TranslationProvider` в интеграционных тестах —
запрещены конституцией проекта, поскольку скрывают дрейф контракта с реальными on-device API;
используются только в unit-тестах пайплайна (не в integration).
